## Frontend

- **Стек:** Vite + React 19 + TypeScript, MUI (компоненты и иконки), axios (HTTP-клиент),
  date-fns (работа с RFC 3339 / UTC / локальным временем), Zustand (стор броней), MSW
  (моки на этапе dev/до появления backend), clsx (объединение CSS-классов).
- **Подход к разработке:** folder-by-type структура (`components/pages/api/hooks/store/utils`),
  переиспользуемые презентационные компоненты (Button, Header, RoomsTable, AssetsTable),
  бизнес-логика (проверка пересечений, конвертация времени) вынесена в чистые функции `utils/`.
  Состояние броней — в Zustand-сторе, обращающемся к `api/bookingsApi.ts`.
- Сложнее всего оказалось разобраться с конвертацией времени между UTC (хранение и API) и
  локальной таймзоной пользователя: на первый взгляд простая задача, но всплывает во всех
  местах — в форме, в таблице, в фильтре по дате. Пришлось вынести все преобразования в
  `utils/date.ts` и строго разделить «что хранится» и «что показывается».
- Если бы делал заново — раньше вынес бы API-слой в отдельный модуль с типами, общими с
  backend (через пакет или хотя бы копию `types.ts`). Сейчас часть типов продублирована, и
  при изменении контракта приходится синхронизировать вручную.

## Backend

- **Стек:** Node.js 22 + Express + TypeScript, хранилище — SQLite (better-sqlite3) с файлом
  на диске, валидация входных данных через zod-схемы, CORS настроен через переменную
  окружения `CORS_ORIGIN`.
- **Подход к разработке:** структура `routes/` (по одному файлу на ресурс: rooms, assets,
  bookings) + `services/` с бизнес-логикой (проверка пересечений интервалов, генерация id),
  + `db/` со схемой и миграциями. Проверка пересечений выполняется на сервере перед вставкой:
  для брони берётся ресурс и интервал, ищутся пересекающиеся брони того же ресурса
  (`start < newEnd AND end > newStart`), при находке возвращается 409 Conflict. Ошибки
  централизованно обрабатываются middleware: 400 на невалидный payload, 404 на отсутствующий
  id, 409 на конфликт, 500 на непредвиденное. Такой подход гарантирует, что даже при обходе
  фронта напрямую через API создать некорректную бронь нельзя.

## CI/CD своими словами

- При каждом пуше в `main` GitHub Actions (`frontend-deploy.yml`) собирает статическую сборку
  фронтенда (`npm run build`) и публикует её на GitHub Pages.
- Backend деплоится на Render автоматически при пуше в подключённую ветку (или через deploy hook
  из Actions) — Render пересобирает Docker-образ/Node-приложение и перезапускает сервис.
- Frontend и backend деплоятся независимо друг от друга и общаются по HTTPS; адрес backend
  передаётся во frontend через переменную окружения `VITE_API_URL` на этапе сборки.

## Какая тема оказалась самой интересной

Интереснее всего было возиться с CI/CD. Когда я только начинал, «деплой» казался магией: где-то
на сервере что-то запускается, и сайт доступен по ссылке. Разобравшись с GitHub Actions,
Render и переменными окружения, я увидел, что это просто цепочка понятных шагов: собрать,
положить артефакт в нужное место, прокинуть конфиг. Особенно понравилось ловить реальные
проблемы — например, когда фронт «пропал» из-за неправильного `base` в Vite или когда
`VITE_API_URL` не подхватывался, потому что переменная была создана во вкладке Secrets вместо
Variables. Каждая такая отладка давала понимание, как всё устроено изнутри. Планирую дальше
развиваться в этом направлении: хочу попробовать полный pipeline с тестами и превью-деплоем
на каждый PR.

## Пожелания по курсу

Хотелось бы больше практики именно по CI/CD: показать на живом примере, как связать
несколько workflow (lint, test, build, deploy), как делать preview-окружения для PR и как
организовать секреты/переменные так, чтобы не путаться. Ещё было бы полезно разобрать типовые
ошибки деплоя (CORS, base path, кэш браузера) — я столкнулся почти со всеми и решал их
методом тыка.

## Известные ограничения реализации

- Backend хранит данные в SQLite-файле на диске Render; конкурентный доступ обрабатывается
  самой SQLite через блокировки на запись, но при большом количестве одновременных записей
  это может стать узким местом — для продакшена понадобилась бы нормальная СУБД (PostgreSQL).
- Аутентификация — упрощённая (без реальной проверки пароля/JWT), только для демонстрации UX.
- Пагинация реализована на уровне API (`?page=`, `?limit=`), но в UI пока отображается только
  первая страница; полноценная подгрузка «по кнопке» запланирована, но не сделана.
- Импорт JSON полностью заменяет данные в сторе (не merge) — это осознанное упрощение,
  описано в `docs/SPEC.md`.
