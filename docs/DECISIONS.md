# DECISIONS.md — выбор стека и версии инструментов

## Frontend

- **Vite + React + TypeScript** — быстрый dev-сервер, простая прод-сборка в статику,
  подходит для GH Pages. Строгая типизация TS снижает число ошибок на этапе разработки.
- **MUI (Material UI)** — готовые стилизованные компоненты (Table, Chip, Dialog), не нужно
  писать дизайн-систему с нуля.
- **Zustand** — минималистичное глобальное состояние для броней (без boilerplate Redux).
- **axios** — единый HTTP-клиент с интерсепторами.
- **date-fns** — работа с RFC 3339 / UTC / локальным отображением времени.
- **MSW (Mock Service Worker)** — на этапе Lab 1 позволял работать без backend; на итоговом
  этапе используется только в dev-режиме (`import.meta.env.DEV`), в проде — реальный backend.

### Хранение на этапе Lab 1: IndexedDB vs localStorage
Выбрал **IndexedDB**. Причины: асинхронный API не блокирует главный поток даже при чтении
нескольких сотен броней; поддерживает структурированные объекты и индексы (что удобно, если
понадобится фильтрация по дате/ресурсу прямо в браузере); объём хранилища существенно больше,
чем у localStorage. `localStorage` синхронен и хранит только строки, поэтому его логично
использовать лишь для маленьких простых данных — например, для профиля пользователя или
флага «тёмная тема», что в проекте и сделано в auth-контексте.

## Backend

- **Node.js + Express + TypeScript** — тот же язык, что и на фронтенде (переиспользование
  типов, единый CI), Express — минимальный и предсказуемый фреймворк.
- **Хранилище**: **SQLite** (через `better-sqlite3`). Причины: нулевая конфигурация — база
  лежит одним файлом и легко переносится между dev и Render Disk; транзакции и UNIQUE-индексы
  дают гарантии целостности при проверке пересечений; синхронный API `better-sqlite3` проще
  в коде, чем асинхронные ORM, и не нужен для нагрузок уровня учебного проекта. Если проект
  вырастет — миграция на PostgreSQL по тому же контракту REST-эндпоинтов пройдёт без правок
  на фронтенде.

## Известные ограничения

- Аутентификация упрощённая: пользователь вводит имя, оно сохраняется в `localStorage`, но
  серверных проверок и JWT нет — этого достаточно для демонстрации UX, но не для продакшена.
- SQLite-файл на free-плане Render лежит на персистентном диске небольшого размера; при
  превышении лимита запись упадёт — для реальной нагрузки нужна управляемая СУБД.
- Пагинация реализована в API, но UI показывает только первую страницу; догрузка не сделана.
- Список ресурсов (аудиторий/инвентаря) редактируется только через импорт JSON — отдельных
  CRUD-эндпоинтов для rooms/assets нет, потому что по заданию это не требовалось.
- Нет интеграционных автотестов backend — проверка пересечений покрыта только ручными
  сценариями из `docs/TESTS.md`.
